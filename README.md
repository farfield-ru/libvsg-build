# libvsg-build

Build scripts and CI pipeline that compile the
[VulkanSceneGraph](https://github.com/vsg-dev/VulkanSceneGraph) stack as
**static (PIC) libraries** for **Linux (x64)** and **Windows (x64, MSVC)** and
publish the binaries as GitHub Release assets, consumable through a **single
dependency-free CMake config**. Companion to
[libocct-build](https://github.com/farfield-ru/libocct-build), for the same
consumer ([modeuler-ng](https://github.com/farfield-ru/modeuler-ng)).

## What is built

One install prefix per configuration (`vsg-<BuildType>/`) containing:

| Component | Tag | Form | Why |
|---|---|---|---|
| [VulkanSceneGraph](https://github.com/vsg-dev/VulkanSceneGraph) | `v1.1.15` | **static (PIC)** | Core scene graph / Vulkan renderer |
| [vsgXchange](https://github.com/vsg-dev/vsgXchange) | `v1.1.13` | **static (PIC)** | Asset readers/writers (`vsgXchange::all`) |
| [vsgImGui](https://github.com/vsg-dev/vsgImGui) | `v0.7.0` | **static (PIC)** | Dear ImGui + ImPlot integration (imgui/implot compiled in from its pinned submodules) |
| [Vulkan-Headers](https://github.com/KhronosGroup/Vulkan-Headers) | `vulkan-sdk-1.4.341.0` | headers | vsg headers include `<vulkan/vulkan.h>` |
| [Vulkan-Loader](https://github.com/KhronosGroup/Vulkan-Loader) | `vulkan-sdk-1.4.341.0` | **link artifact only** (`libvulkan.so` / `vulkan-1.lib`) | Consumers link it; the *runtime* loader stays the host's |
| [glslang](https://github.com/KhronosGroup/glslang) | `16.3.0` | static (PIC) | Runtime GLSL→SPIR-V compiler (`VSG_SUPPORTS_ShaderCompiler`) |
| [assimp](https://github.com/assimp/assimp) | `v6.0.4` | static (PIC) | Model importers for the vsgXchange assimp reader |

Tags are pinned in `scripts/build.*` and `.github/workflows/build.yml`, and
match the versions modeuler-ng previously received from vcpkg (baseline
`9e53836`).

- Configurations: `Release`, `Debug`, `RelWithDebInfo` (per-config archive
  name postfixes `d` / `rd` come from the upstream projects; the shipped
  config references them so consumers never see the difference).
- The MSVC runtime of a Windows consumer must match the archives, so pick the
  archive matching your `CMAKE_BUILD_TYPE` (all archives use the **dynamic
  CRT**: `/MD`, `/MDd` for Debug — set explicitly, not inherited from CMake's
  default); on Linux the Release archive links cleanly into any app build
  type.

## Why static (issue #4)

The previous shared-library artifact made every consumer stage libraries to
each binary directory, manage `$ORIGIN` rpaths, and re-find Vulkan, glslang
and xcb at configure time — the consumer integration produced three review
rounds of defects almost entirely in those two categories. Static archives
with an absorbed link line delete the whole problem class: nothing to stage,
no rpath, no transitive `find_package`. Integration cost scales with how many
places a dependency touches the consumer's build, not with the library's
size.

Trade-offs accepted there: each consumer binary carries its own copy (the
pre-migration status quo), links are slower, loads faster, and VSG cannot be
swapped without relinking.

## One package config, zero lookups

The prefix ships exactly **one** CMake file, `lib/cmake/vsgall/vsgallConfig.cmake`,
generated by the build scripts. It defines a single imported target stating
the entire static link line in order — every archive by path inside the
prefix, plus (Linux) the plain system library names `xcb`, `pthread`, `dl`
that the linker resolves itself. It contains **no**
`find_dependency`/`find_package`/`pkg_check_modules`, and the build fails if
one appears or if any other `.cmake` file survives into the archive. The
upstream per-package configs (which would re-find Vulkan, glslang and xcb) are
removed.

```cmake
find_package(vsgall CONFIG REQUIRED)     # target vsgall::vsgall
target_link_libraries(app PRIVATE vsgall::vsgall)
```

C++17 is propagated through the target. Consumers include `<vsg/...>`,
`<vsgXchange/...>`, `<vsgImGui/imgui.h>` as usual — vsgImGui's imgui/implot
are compiled into its archive, so the full ImGui/ImPlot API is available
without a separate imgui package.

## Vulkan: headers + link artifact, no runtime loader

Vulkan is built from pinned Khronos tags, so neither this repo's CI nor
consumers need a Vulkan SDK. The prefix carries `include/vulkan` and the
**link** artifact (`lib/libvulkan.so` with SONAME `libvulkan.so.1`, or
`lib/vulkan-1.lib`). The **runtime** loader is deliberately not shipped: it
is a driver-integration component owned by the host system, like libGL —
exactly the boundary the Vulkan SDK itself draws. At run time the dynamic
linker resolves `libvulkan.so.1` / `vulkan-1.dll` from the system (Linux:
`libvulkan1` or the GPU driver stack; Windows: GPU drivers install it).
The CI smoke test takes its runtime loader from the loader's own build tree —
runtime provisioning belongs to the build environment, not the artifact.

On Linux the link artifact is built with **XCB WSI only**, matching exactly
what the previously-consumed loader exported (`vkCreateXcbSurfaceKHR` +
`vkCreateDisplayPlaneSurfaceKHR`; no Xlib, no Wayland). VSG creates its
surface from an `xcb_window_t`.

## Hidden symbol visibility (Linux)

All static archives are compiled with
`-fvisibility=hidden -fvisibility-inlines-hidden`. Their objects end up
inside consumers' *shared* objects, and with default visibility every
absorbed vsg/glslang/assimp/zlib symbol becomes an export of that library —
modeuler-ng's `libmodeuler_ng.so` measurably exported 521 foreign symbols
(`adler32`, `aiGetMaterialColor`, …), a live collision hazard for anything
else in the process. The smoke test links the archives into a shared library
and fails the build if absorbed-dependency symbols appear in its dynamic
symbol table (which also proves the archives are PIC). Windows needs no
equivalent: DLLs export nothing that is not `__declspec(dllexport)`ed.

### Feature choices (parity with modeuler-ng's vcpkg manifest)

- **vsg**: windowing ON (xcb on Linux, native Win32 on Windows), shader
  compiler ON (glslang), shader *optimizer* **pre-seeded OFF** (no
  SPIRV-Tools, same as vcpkg's plain `glslang` dependency). Upstream defaults
  `VSG_SUPPORTS_ShaderOptimizer` ON and keeps it whenever
  `find_package(SPIRV-Tools-opt)` succeeds, so on a host with a Vulkan SDK it
  would otherwise be enabled by accident, making the artifact depend on a
  SPIRV-Tools it does not ship. The build **fails** if VSG silently drops the
  shader compiler (it only warns when glslang is missing) or if the optimizer
  sneaks back in.
- **vsgXchange**: `assimp` reader ON — every other optional dependency
  (freetype, curl, GDAL, OpenEXR, KTX, draco, OSG) is pre-seeded OFF so a
  library found on the build host can never leak into the artifact. The
  dependency-free built-in readers (stbi, dds, ktx-read, glTF, 3DTiles, cpp,
  bin) are always present. The build fails if assimp is not picked up
  (vsgXchange would otherwise silently ship a stub reader).
- **vsgImGui**: `SHOW_DEMO_WINDOW=OFF` (`ImGui::ShowDemoWindow` is a stub),
  matching the vcpkg port.

### Consumer smoke test

Every configuration builds `scripts/smoke/` against the finished install
prefix — `find_package(vsgall)`, compile, link, run — before the archive is
packaged, in a **scrubbed environment** (`env -i` on Linux; on Windows the
MSVC environment must survive, so `VULKAN_SDK`, `CMAKE_PREFIX_PATH` and the
vcpkg variables are unset instead) with `CMAKE_PREFIX_PATH` set to the
install dir alone. Anything the prefix fails to provide surfaces in this
build, not in a consumer. Beyond compiling and linking, the test asserts that
the absorbed assimp importers are actually registered at run time (a `.obj`
reader must answer — static archives can silently drop registration
objects), and on Linux links everything into a shared library to enforce the
PIC and hidden-visibility properties above.

## Consuming

Point `CMAKE_PREFIX_PATH` at the extracted prefix; then

```cmake
find_package(vsgall CONFIG REQUIRED)     # target vsgall::vsgall
```

Nothing else is looked up, on either platform: no Vulkan SDK, no
`libvulkan-dev`, no glslang, no pkg-config. What the host must still provide:

- **Linux, link time**: `libxcb` (the config names `xcb` on the link line, so
  `libxcb1-dev` — no `xcb.pc` / pkg-config involved).
- **Run time**: a system Vulkan runtime loader — `libvulkan.so.1` from
  `libvulkan1` or the GPU driver stack on Linux; `vulkan-1.dll` from the GPU
  driver on Windows.

Layout: archives in `lib/` (Linux also `lib/libvulkan.so`, the Vulkan link
artifact), headers in `include/`, the config in `lib/cmake/vsgall/`.
`bin/vsgconv` (vsgXchange's converter, statically linked) doubles as a quick
sanity check of the archives.

## Optimization

- Linux Release adds `-march=x86-64-v2` (requires an SSE4.2-era CPU, roughly
  2009 or newer) — same distribution baseline as libocct-build.
- No LTO: upstream ships no LTO profile for these libraries (unlike OCCT's
  `BUILD_OPT_PROFILE=Production`), and the expected win is small relative to
  the toolchain risk.

## Patches

`patches/<component>/*.patch` (component ∈ `vulkan-headers`, `vulkan-loader`,
`glslang`, `assimp`, `vsg`, `vsgxchange`, `vsgimgui`) are applied with
`git apply` after cloning the upstream tag. Currently empty.

## Local build

Linux (needs cmake, ninja, git, pkg-config, libxcb1-dev — pkg-config and the
xcb dev package are build-time needs of vsg itself; consumers of the artifact
need neither):

```sh
./scripts/build.sh Release        # or Debug / RelWithDebInfo
```

Windows (from an *x64 Native Tools* developer prompt, requires Ninja — no
Vulkan SDK):

```powershell
.\scripts\build.ps1 -BuildType Release
```

The script clones the pinned tags, builds in dependency order
(Vulkan-Headers → Vulkan-Loader → glslang → assimp → vsg → vsgXchange →
vsgImGui), installs into `_work/install/vsg-<BuildType>/`, generates
`vsgallConfig.cmake`, strips everything package-shaped that upstream installs
left behind, runs the smoke test and packages an archive into `_work/dist/`.

## CI

`.github/workflows/build.yml` runs a 2 (OS) × 3 (build type) matrix on every
push to `main` (and on manual dispatch), uploads each build as a workflow
artifact, and then creates/updates the `vsg-<VSG_TAG>` GitHub Release with all
six archives.

Windows builds are pinned to `windows-2022` (VS 2022, MSVC 14.4x): the
VS 2026 toolset currently on `windows-latest` (MSVC 14.51) has a documented
known issue — *"cl.exe hangs compiling some source files"* — and
deterministically hangs on assimp's vendored contrib sources. The MSVC 14.x
ABI is stable, so VS 2026 consumers link these archives without issues. Move
back to `windows-latest` once the MSVC fix ships.

## Upgrading

Change the tags in `.github/workflows/build.yml` (and the defaults in
`scripts/build.sh` / `scripts/build.ps1`), push to `main`, and a new release
`vsg-<tag>` is produced. Mind upstream's cross-version constraints:
vsgXchange `v1.1.13` requires vsg ≥ 1.1.14, vsgImGui `v0.7.0` requires
vsg ≥ 1.1.10, vsgXchange requires assimp ≥ 5.1. The glslang archive list in
the generated config is discovered, not hardcoded, but `pick_lib` only checks
that a **file exists**, not that it contains anything. glslang 16.3.0 has
already consolidated its code into `libglslang.a`, and `libSPIRV.a`,
`libMachineIndependent.a`, `libGenericCodeGen.a` and `libOSDependent.a` ship as
~1.4 KB archives holding a single stub object — so a *rename* trips `pick_lib`,
but a further *merge* would not: the stubs would still be found and the link
line would still be generated.

What actually catches a broken glslang set is the smoke test, which compiles a
trivial shader through `vsg::ShaderCompiler` and therefore pulls those archives
and exercises their order in the generated link line. Keep the candidate lists
in both scripts up to date on a rename; rely on the smoke test for the rest.
